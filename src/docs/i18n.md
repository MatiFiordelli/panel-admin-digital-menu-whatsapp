# Traducciones (es / en / pt / zh)

## Cómo funciona
`i18next` con un archivo JSON por idioma en `src/core/i18n/locales/`. Se carga solo el idioma activo (carga diferida). **Español es la referencia**: toda clave nueva se agrega en los cuatro archivos.
Las notificaciones guardan la clave y los parámetros, no el texto, así que siempre se muestran en el idioma actual (ver `notifications-and-gestures.md`).

## ¿Usar una librería de traducción automática?
- **En tiempo de ejecución, no.** Traducir los textos de la interfaz con un servicio en el navegador agrega peso, latencia, costo y dependencia, expone claves de API, puede equivocar términos
  (p. ej. «Entrar» como acción vs «Gestionar») y no se puede revisar. La interfaz usa textos fijos, revisados una vez.
- **En tiempo de desarrollo, sí es razonable** para BORRADORES: generar la traducción con una herramienta (DeepL, un modelo de lenguaje) y que una persona que hable el idioma la revise, sobre todo portugués y chino.
  Esa es la forma en que se escribieron los textos actuales (redactados con IA, sin revisión de hablantes nativos todavía: pendiente).
- **Contenido de los negocios** (título y descripción por idioma): una función opcional «Traducir» en el formulario de edición sí podría usar un servicio, pero la llamada debe hacerla el servidor de la API (para no exponer claves) y el resultado se revisa antes de guardar. No está planificada.
- **Nombres de países, monedas y fechas:** no se traducen a mano; los entrega el navegador (`Intl.DisplayNames`, `Intl.DateTimeFormat`) en el idioma actual.

## Verificación automática
`node scripts/check-i18n.mjs` compara todos los idiomas contra español: claves faltantes, sobrantes y `{{parámetros}}` que no coinciden. Sale con error si algo falla.
Agregar a `package.json`: `"i18n:check": "node scripts/check-i18n.mjs"` y correrlo antes de cada commit que toque textos.
